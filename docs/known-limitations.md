# Known limitations

What the system does not do, or does with a caveat worth knowing before relying on it.
Nothing here is a to-do disguised as a limitation; each item is a real property of the
current code.

---

## Location and tracking

1. **Foreground only.** The app reports a fix while Home or Trip is on screen. A
   backgrounded or force-quit app stops reporting until it is opened again. There is
   no background task and no permission for one, so a crew that switches to a phone
   call is temporarily invisible.
2. **A stale position is never hidden, but it is also not corrected.** If the phone
   stops reporting, the admin map keeps the last known marker, greyed, and says the
   position is historical. There is no dead-reckoning or interpolation.
3. **Accuracy is whatever the phone reports.** A fix within 100 m is labelled `good`
   and a fix up to 1000 m `poor`; the server cannot verify the claim.
4. **GPS spoofing is not detected reliably.** Range, speed and jump checks catch gross
   inconsistencies only (§5 of `docs/security.md`).
5. **No background upload after an app kill.** The buffer survives a restart, but a
   fix older than two minutes is discarded rather than uploaded: the phone sends the
   newest useful position, not a full reconstruction of the gap.

## Transport and real-time behaviour

6. **Polling, not push.** The admin overlay polls every 5 seconds, so a position can
   be up to 5 seconds old on screen even when everything is healthy. Every open tab
   costs one request per 5 seconds.
7. **A newly activated response appears within 30 seconds.** The cursor only advances
   when a position changes, so the client does a full poll every sixth tick to pick up
   responses that have no fix yet.
8. **The crew's phone is not told about a server-side route recalculation.** It keeps
   the geometry it received with the assignment until it reloads that response. The
   admin map and the phone can therefore disagree about the active route.

## Routing

9. **No traffic awareness.** OSRM's public server routes on a static road graph. The
   interface never claims otherwise; nothing here is a live traffic estimate.
10. **Deviation is line-of-sight to the polyline.** A parallel road 150 m away is
    "on route". There is no map matching, no turn-by-turn comparison, no heading
    consistency check.
11. **Provider dependency.** Route resolution needs OSRM; address lookup needs
    Nominatim and Photon. If they are unreachable, routes fail and are marked
    degraded, address search degrades to manual coordinates, and browser maps need
    internet access for tiles.

## Scale

12. **SQLite with one writer.** Comfortable to roughly 100 concurrently active
    vehicles (about 1,200 writes a minute). At 1,000 the write lock is the bottleneck;
    10,000 is out of scope for this deployment. See `docs/phase-c.md` §16.
13. **One Flask process.** No in-memory fan-out between workers, which is part of why
    polling was chosen over WebSockets.
14. **The live positions payload grows with the fleet**, not with changes: at 1,000
    active vehicles a full poll is roughly 200 KB per tab.

## Operational

15. **No unit token rotation.** The token is derived from the call sign; rotating it
    means renaming the vehicle.
16. **No rate limiting on the driver API.** A valid token can post as fast as it likes.
17. **The watchdog sweep is manual or external.** `POST /api/maintenance/expire-stale`
    must be called by something (cron, a monitoring probe). Nothing schedules it
    in-process.
18. **`requirements.txt` is pinned but not audited.** There is no dependency
    vulnerability scan in the repository.
19. **The development server is Flask's.** `python app.py` runs with the debug
    reloader; it must not be exposed as-is.

## Presentation and content

20. **No licence has been selected.** Until one is added, no permission is granted for
    reuse beyond applicable law.
21. **Screenshots in `screenshots/` are manual captures**, not generated by a test; the
    navigation sidebar is cropped out of them.
    They can drift from the interface.
22. **The admin UI is desktop-first.** It works on a tablet; it was not designed for a
    phone browser.
